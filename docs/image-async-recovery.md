# 全线路生图异步与断网恢复

此版本覆盖本站登录用户的 VIP 和画布：文生图、参考图、编辑，以及 GPT Image、Gemini 原生等现有图片线路。视频和提示词工具沿用原流程。原来允许不登录、自带 API Key 的调用继续兼容旧同步接口；账号任务恢复适用于本站登录用户。旧 API 不传 `asyncTask` 时继续保持原接口行为。

## 用户能看到的变化

- 完整上传请求后，本站先保存任务并返回任务编号，再由后台生成。无需让浏览器等待整张图片的长连接。
- 断网、切换标签、刷新、关闭页面都不取消已经受理的任务。登录同一账号后恢复结果；短暂查询断线显示连接恢复。
- 提交回执丢失时使用原请求编号核对。服务器未受理时，用完全相同的编号和内容重发，防止重复生成与扣点。
- 尚未受理的上传内容只在 IndexedDB 暂存，按账号隔离，不写入 localStorage；确认受理后删除。自动恢复上传限于 20 分钟，过期显示未确认受理，避免隔日意外发起付费生成。
- 图片先提供可用结果地址。Base64 原图在本站落盘后返回地址；远程原图在后台暂存，完成后替换为本站地址。预览与原图分开，不重复在 JSON 中传大图。
- 上游明确失败由后台结算并退回本站扣点；查询断线不会被当成生成失败。生成成功但本站保存异常会单独提示，不伪称上游失败。

## 部署

新增模块已经加入 Dockerfile；Compose 将 `./storage/image-jobs` 挂载到 `/app/storage/image-jobs`。该目录包括请求文件、结果原图、预览、结果恢复日志和签名密钥，必须保留。生产任务元数据存入现有 MySQL，启动时自动建 `image_jobs` 表；无需 Redis 或手工迁移命令。

服务器更新到 `codex/image-assets-recovery` 分支（同时包含画布进度条与并发调整）：

```bash
set -e
cd /www/wwwroot/aigc.aittco.com
git status --short
git fetch origin
git switch codex/image-assets-recovery
git pull --ff-only origin codex/image-assets-recovery
touch .env
set_env() {
  if grep -q "^${1}=" .env; then
    sed -i "s/^${1}=.*/${1}=${2}/" .env
  else
    printf '\n%s=%s\n' "$1" "$2" >> .env
  fi
}
set_env IMAGE_JOB_CONCURRENCY 48
set_env IMAGE_JOB_USER_CONCURRENCY 6
set_env IMAGE_JOB_MAX_QUEUED 200
set_env IMAGE_JOB_USER_MAX_QUEUED 32
docker compose up -d --build app
docker compose ps
docker compose logs --tail=100 app
```

若服务器有本地 Git 改动，先保存并核对这些改动再切换，不要使用强制重置。不要删除 `.env`、数据库卷、`uploads` 或 `storage`。更新后网页按 Ctrl+F5，确保 VIP 页面也加载新的脚本。

## 默认参数与范围

| 参数 | 默认 | 作用 |
| --- | --- | --- |
| IMAGE_JOB_CONCURRENCY | 48 | 全站同时执行的图片任务数（上限 64）；任务主要在等上游，按上游渠道允许的并发设置 |
| IMAGE_JOB_USER_CONCURRENCY | 6 | 单个用户同时执行的任务数；超出的排队，不占用其他用户的名额 |
| IMAGE_JOB_MAX_QUEUED | 200 | 全站最大排队任务数，超限拒绝受理 |
| IMAGE_JOB_USER_MAX_QUEUED | 32 | 单个用户排队加执行中的任务上限，超限提示稍后提交 |
| IMAGE_JOB_MAX_REQUEST_BYTES | 50 MiB | 单次请求上传上限 |
| IMAGE_JOB_DEADLINE_MS | 1200000 | 从受理算起的最终任务期限，20 分钟 |
| IMAGE_JOB_POLL_INTERVAL_MS | 2000 | 后台原生任务查询间隔 |
| IMAGE_JOB_RETENTION_MS | 18000000 | 原图及原图访问签名默认保留 5 小时；任务历史和预览继续保留 |
| LINE4_LOCAL_STORAGE_TTL_HOURS | 5 | 第四线路原有本站图片暂存期限 |

原图默认暂存 5 小时，页面提示“图片云端仅保留 4 小时，请尽快下载到本地”，留 1 小时缓冲。原图签名到期后拒绝读取，文件由定时维护清理回收；第四线路也有后台清理。2026-10-16 的修复使历史记录和预览缩略图长期保留，过期原图不会连带删除预览与历史记录。现有保留期限配置继续生效，本次更新只设置上述四个并发参数。

单用户上限统计排队与执行中的任务，重复的请求编号仍返回原回执，不新增任务。超限返回 HTTP 429 与 `USER_QUEUE_FULL`，两种界面都显示提示并停止自动重试。用户并发名额用满时会跳过该用户，继续调度其他用户。并发设置仅作用于登录用户的持久图片任务，视频和旧同步 API 不经过此队列。

当前后台队列用于单个 app 容器、单 Node 进程。不要直接改为多个副本或 PM2 cluster：本版尚无跨进程任务领取锁，共享同一 MySQL 的多个执行器可能重复处理任务。

服务重启会恢复排队任务和已经得到上游任务编号的任务。无法追踪的同步调用若在重启时中断，停止重发并补偿本站扣点；上游是否实际出图可能无法判断。上游已明确返回图片后，生成成功与图片保存状态分别保存；如果此时原图尚未落盘就发生断电/磁盘故障，可能需要管理员核对，不能保证找回所有仅存在于内存中的图片。

## 上线验证

1. 在 VIP 和画布分别提交一张图，检查从“提交中”进入“后台生成中”，最终有图片。
2. 在生成中切换到其他标签，等待后返回；再测试受理后刷新、关闭后重新打开。任务应恢复，扣点只有一次。
3. 在浏览器开发者工具 Network 选择 Offline，恢复 Online 后应继续查询；不能因 `Failed to fetch` 直接显示上游生成失败。
4. 每个已启用模型/线路至少验证一次；参考图和编辑另测一次。Gemini 批量请求逐张提交，每张独立任务和费用。
5. 生成成功后查看历史记录与下载原图；等待后台保存后，原图地址可更新到 `/api/image-job-assets/...`，预览不影响原图下载。
6. 账号 A 生成中切换到账号 B（也包括其他标签登录），B 不应收到 A 的结果或重发 A 的上传；回到 A 应恢复原任务。
7. 对真实失败任务核对本站流水：一次扣点、一次退款；此次改动不自动补偿旧账单。

首期覆盖登录用户持久图片任务；视频、匿名/旧同步图片、浏览器预览加载错误明确标为未覆盖。上线前历史不回填，采集缺失或过期显示异常，不推算假数据。本地无 MySQL 时并发仍可用，长期历史显示“未采集/不可用”。看板读取不触发上游请求、重试、退款或账务修改。

### 主机采集器与部署

应用只读取 storage/operations/host.json，目录以只读方式挂载。Linux 宿主机运行轻量 Python 标准库采集器，通过 systemd 每 20 秒采集 /proc CPU、内存和 app/MySQL 容器状态，原子替换快照。Docker 状态命令每次超时 3 秒，只写状态枚举，不输出环境变量或凭证；应用不挂载 Docker socket。Node RSS/堆内存/事件循环、cgroup 内存、图片卷剩余容量由应用采集。数据库耗时表示后台聚合耗时，不冒充连接池等待。未安装主机采集器显示不可用。

在服务器仓库目录执行（需服务器已取得本次提交；等待当前生成任务完成后重建 app）：

```sh
mkdir -p storage/operations
sudo sh scripts/install-host-operations.sh
docker compose config --quiet
docker compose up -d --build --no-deps app
docker compose logs --tail=100 app
systemctl status image-operations-collector.timer --no-pager
```

应用和 MySQL 的 Docker 日志均限制为 10 MB × 3 份；应用文件日志也限制为 10 MB × 3 份。新日志设置在对应容器重建后生效；上述命令仅重建 app，MySQL 请在计划维护窗口重建。现有 MySQL 数据卷、图片卷不变。限流日志不再记录原 API Key/会话 token。管理员查询不会暴露完整提示词、参考图、请求体、Authorization、签名图片 URL 或原始响应。

验收：打开两个管理员页面，核对 48/6 等实际生效预算；模拟本站队列、上游队列、429/5xx/超时/保存失败/结算等待，确认分类、用户、时间线；页面隐藏后应停止请求；数据库或主机采集停止时应显示不可用/过期而非零。近 5 分钟线路至少 10 个终结样本且失败率≥20%触发站内告警；资源和队列异常采用持续时间门槛。告警在后台独立检查，不依赖管理员开页面。

回退前等待运行任务结束；切回前一应用版本并重建 app，保留 ops 表和持久卷。停止采集器可执行 `sudo systemctl disable --now image-operations-collector.timer`，无需删除历史数据。

### 数据新鲜度与故障恢复

15 分钟和 1 小时等短窗摘要每分钟聚合；24 小时和 7 天故障摘要每 15 分钟聚合，并各自携带真实更新时间，不用短窗刷新时间冒充长窗新鲜度。浏览器 100 秒刷新读取现有趋势缓存，不强制数据库重新统计。线路 P95 是可合并耗时分桶的上界估计，不能解释为毫秒级精确分位数。

事件按安全任务版本防重；状态写入失败由后台有界缓冲重试。终态任务清理前必须确认摘要及事件归档成功；归档失败或超时保留原元数据，后续维护继续尝试，不阻塞其他任务。进程崩溃可能丢失内存中尚未写入的中间阶段事件，保留的终态任务可在清理时补归档；看板会提示采集缺口，不保证恢复完整中间时间线。
