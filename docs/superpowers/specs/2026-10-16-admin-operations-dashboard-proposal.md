# 管理员运行与运营数据看板方案

日期：2026-10-16。状态：方案提案，待确认实施范围。

适用环境：现有 React 管理员后台、单 Node 进程、Docker Compose、同机 MySQL，服务器 4 核 / 8 GB。仓库当前图片任务默认并发为全站 48、单用户 6；上线看板必须读取服务器实际生效值。

## 1. 目标与推荐方案

扩展现有后台，让管理员能完成“发现异常 → 找到线路、任务和受影响用户 → 核对图片与账务 → 处理 → 确认恢复”。首页同时回答容量是否够、用户体验是否下降、哪条线路拖累网站、异常是否造成用户损失。

推荐复用现有后台、任务服务与 MySQL，增加独立的运行统计、任务摘要和结构化故障事件。先完成运行诊断，再完善用户经营分析。首期沿用单进程部署，不增加任务执行器。

## 2. 现有能力与必须纠正的口径

| 当前情况 | 对方案的影响 |
| --- | --- |
| 已有 `/admin`、运行总览、用户详情、线路与模型管理 | 原位扩展，保留现有管理入口 |
| `/api/admin/dashboard` 已有管理员鉴权、默认 15 秒缓存和请求合并；页面目前约 120 秒刷新 | 运营统计可以复用；实时运行摘要单独刷新 |
| 现有“成功率”以未退款扣款占比计算 | 改名为账务指标；生成结果按任务终态另算，未完成任务不算成功 |
| 现有 `pendingTasks` 来自旧 `billing_pending_tasks`，新持久图片任务没有全部登记进去 | 从图片任务服务与持久任务状态采集真实队列，避免漏计 |
| 图片任务公开接口把上游排队也显示为 `queued` | 管理员读取内部阶段，区分本站排队和上游排队 |
| 任务元数据默认约 5 小时后按创建时间清理，原图保留也有单独期限 | 运行表用于调度，历史看板使用独立摘要与聚合，不能直接扫描运行表做 7 天趋势 |
| 日志有 JSON 文件、控制台与管理员变更记录，但关联字段不统一，部分字段可能包含凭证 | 故障中心读取经过字段白名单和脱敏的结构化事件 |
| 现有“在线”表示近 5 分钟会话活跃人数；账号 active 表示账号可用 | 页面明确标注定义，分别展示近期访问人数、账号状态和实际生成用户 |

历史扣款、兑换和退款可继续查询。上线前已清理掉的任务阶段、错误细节和精确耗时显示“历史数据不足”，不倒推成完整统计。

## 3. 页面与核心数据

保留现有后台导航，扩展“运行看板”“任务与故障”“运营统计”；用户、线路和模型管理继续承接详情及配置操作。

### 3.1 运行看板：每天先看这一页

顶部固定展示：并发占用 / 生效上限、本站排队数、最长排队时间、近 15 分钟任务成功率、失败用户数、未恢复告警数。每张卡片都可进入带好筛选条件的明细。

| 区域 | 展示的数据 | 能回答的问题 |
| --- | --- | --- |
| 容量与排队 | 实际占用名额、全站和单用户限制、本站排队、上游排队、活跃生成用户、每用户占用、个人/全站队满拒绝次数 | 是网站容量不足，还是上游慢、单个用户批量提交？ |
| 体验趋势 | 每分钟受理与完成任务数、成功率、P50/P95 排队和生成耗时、当前最老任务、超时数 | 排队和出图是否越来越慢？ |
| 故障摘要 | 失败原因 Top 5、异常线路、受影响用户数、原图/预览保存异常、待结算/待退款 | 现在最该处理什么？ |
| 线路与模型 | 各线路/模型请求量、任务成功率、P95 耗时、上游 429/5xx、连续失败、正在执行和排队数 | 哪个模型或渠道影响体验，是否应切换？ |
| 主机与应用 | 主机可用内存、CPU、磁盘剩余；app/MySQL 容器状态；Node 内存、事件循环延迟；DB 查询耗时与连接等待 | 继续提高并发是否有资源空间？ |
| 部署与采集状态 | 当前版本、进程启动时间、有效配置及来源、数据更新时间、采集覆盖范围 | 更新是否生效？眼前的数据是否新鲜完整？ |

中间放队列/占用趋势和请求/完成趋势，下方放线路健康表和最近异常。CPU、内存等资源曲线放详情区，首页突出正在影响用户的异常。

### 3.2 任务与故障：定位到具体用户和请求

任务列表支持时间、用户、任务编号、请求编号、图片/视频、VIP/画布、模型、实际线路、阶段、失败类别、保存状态、结算状态筛选。默认每页 50 条，使用游标分页，提供有范围和数量限制的脱敏导出。

每行至少显示：提交时间、用户、任务编号、模型/线路、当前阶段、已等待/已执行时间、失败摘要、扣点、退款/结算状态。

任务详情用时间线串起：受理 → 本站排队 → 派发 → 上游排队/生成 → 确认结果 → 原图保存/预览 → 账务结算。缺少的阶段显示“上游未提供”或“历史未采集”。无阶段变化不直接判为卡死；同时看最后查询时间、最后有效进展和最终期限。

详情关联 `taskId`、`requestId`、`userId`、`accountId`、`chargeId`、`generationRecordId`、上游任务号、上游 traceId。实际执行线路需在解析后写回，提交时未指定的默认线路不能归为未知或凭当前配置猜测。

故障按类别和线路聚合，展示首次/最近发生、发生次数、涉及任务、去重用户数、是否已恢复、处理人和处理记录。列表可显示“待处理 / 处理中 / 待核对 / 已恢复 / 已关闭”，人工关闭不会掩盖仍持续触发的异常。

### 3.3 用户与运营统计：看体验和使用价值

| 数据 | 运营用途 |
| --- | --- |
| 新注册人数、近 5 分钟会话活跃人数、每日实际生成用户 | 区分新增用户、访问用户和真正使用产品的用户 |
| 首次提交率、首次成功率、注册到首次成功耗时 | 找到新用户用不起来的环节；次期补足跨日转化与留存 |
| 失败用户列表、连续失败用户、长期排队用户 | 优先处理已经受影响的用户，进入用户详情核对任务与流水 |
| 模型/线路使用占比、VIP/画布使用占比、成功图片张数 | 判断用户需求和产品功能使用情况 |
| 扣点、退款、净消耗、兑换点数、人工加点、余额不足拒绝 | 核对点数经营和用户使用受阻原因 |
| 次日/7 日再次生成率、使用下降的高频用户、充值后未成功生成用户 | 次期用于留存和服务跟进 |

任务数与图片张数分开统计。用户的页面刷新、重复查询和同请求编号重发不增加任务量。点数消耗不标为现金收入；充值订单实收和上游真实成本接入前不展示营收或利润结论。

## 4. 指标定义

1. **并发占用**：直接取任务服务当前持有的执行名额；包括上游排队、执行/轮询和尚未结束的收尾。DB 的 running 数作为对账值，不能完全替代进程内占用数。
2. **本站排队**：已受理且内部状态为 queued、尚未派发的任务。默认全站排队上限 200；默认用户待处理上限 32 统计其排队加执行。两项均支持环境配置覆盖，看板展示服务实际生效值。
3. **上游排队**：已经占用本站名额、上游明确返回 QUEUED/IN_QUEUE 的任务，是并发占用的子集，不能再次相加。原图下载和预览队列另列。
4. **任务成功率**：所选时间段内终结的任务，成功数 /（成功数 + 失败数）；未终结不进入分母，无样本显示“暂无完成任务”。保留任务对用户呈现的结果与上游已确认/未知结果两个维度；超时不假称上游明确失败。
5. **生成、保存、结算**：三条独立状态轴。生成成功但保存失败显示“生成成功 / 原图保存异常”或“预览异常”；结算失败显示“待结算”，不能归为生成失败并触发退款。
6. **耗时**：本站排队=派发-受理；生成=上游调用发出到确认结果，包含上游排队；结果处理、保存、预览和结算各记时间。现有 completedAt 混有结果处理，历史样本仅标总耗时，不伪称纯生成耗时。
7. **失败原因**：区分本站队满、个人限额、登录/余额/参数拒绝，上游限流、鉴权/余额、内容限制、网络/超时、上游服务错误、结果异常，及本站存储/预览/数据库/结算错误。分类优先使用 code、HTTP 状态和阶段，文本匹配只是兜底。
8. **失败用户数**：选定时间段和筛选条件下按 userId 去重；错误事件数、失败任务数和失败用户数分别展示。同一任务多次轮询失败不等于多张生图失败。
9. **时间窗口**：支持近 15 分钟、1 小时、24 小时、7 天和自定义；今日按 Asia/Shanghai，存储统一 UTC。受理量按受理时间、完结量按终结时间、退款流水按实际退款时间，页面分别标注。
10. **覆盖范围**：首期完整队列监控针对登录用户持久图片任务；视频、匿名/旧同步图片和提示词工具分别标注。视频/旧同步有账本统计不代表已经有完整阶段与并发监控，未采集项显示“未覆盖”。

## 5. 从发现问题到处理

| 发现的情况 | 可定位的信息 | 推荐处理 |
| --- | --- | --- |
| 本站排队持续增加 | 占用、上游排队、最长等待、主机资源、用户分布 | 判断瓶颈；经评估调整预算，不因占用高就自动提并发 |
| 某线路 429/鉴权/余额错误集中 | 实际线路、错误码、发生时间、受影响用户和任务 | 进入线路设置检查配额/凭证、调整默认线路或停用；保留历史和执行中任务 |
| 用户多次失败 | 同用户完整任务、错误、扣点与补偿 | 核对根因及补偿状态；需要重新付费生成时走明确的新请求 |
| 图片已生成但保存失败 | 原图、预览各自阶段和错误，可用结果来源 | 仅恢复保存/预览，不重新生图 |
| 扣点或退款长期未结算 | 原 chargeId、终态、重试记录、账本结果 | 走原幂等结算路径核对并恢复，不直接修改余额/任务 JSON |
| 上游结果未知 | 原上游任务号、最后响应、调用超时点 | 有任务号时核对原任务，无可靠结果时标“待核对” |

首期将“查看用户 / 查看流水 / 查看关联日志 / 进入线路管理 / 记录处理结果”串起来。运行看板查询仅采集数据，不触发上游查询、重试或结算。

次期增加受约束的“核对原任务、重试保存、恢复结算、暂停新派发/恢复、调整并发”。这些操作经同一任务服务执行，防止并行恢复竞态。并发降低只影响后续派发，已有任务继续运行；操作前显示受影响范围与扣费影响，记录操作者、原因和前后值。

并发热调整若开放，采用数据库覆盖值 > 环境变量 > 代码默认值，展示来源并支持清除覆盖。普通管理员查看和记录处理，超级管理员调整线路、并发和账务相关操作。保留全站硬上限与用户公平调度。

## 6. 告警初始规则

以下为建议起始阈值，上线后按真实模型耗时和流量基线调整；表示告警，不直接自动退款、重发或停线路。

| 告警 | 初始触发条件 | 提示 |
| --- | --- | --- |
| 排队异常 | 本站最老任务等待超过 120 秒且连续观察 2 分钟 | 定位用户上限、全站占用与上游排队 |
| 线路质量下降 | 近 5 分钟终结样本 ≥10，任务失败率 ≥20%；或同类硬鉴权错误连续 3 次 | 聚合为一条线路故障，显示样本数和涉及用户 |
| 上游限流 | 同线路上游 429 持续出现 | 与本站个人/全站队满的 HTTP 429 分开 |
| 资源不足 | 主机可用内存低于约 2 GB 持续 5 分钟预警；低于约 1 GB 持续 1 分钟、OOM 或异常重启升级 | 核对 app、MySQL 和系统资源占用 |
| 磁盘不足 | 相关卷可用空间低于 15% 预警，低于 10% 或 2 GB 升级 | 检查原图、预览、日志和数据库增长 |
| 保存/结算积压 | 至少 1 个终态结算等待超过 2 分钟；或至少 5 个保存任务等待超过 2 分钟 | 分清保存与账务，显示年龄和错误 |
| 采集失联 | 数据连续 30 秒没有更新 | 显示“数据过期/状态未知”，不能补零或显示正常 |

告警检查与管理员页面刷新解耦，由服务端后台每 30～60 秒评估一次，并加入少量随机抖动；告警去重、短时抖动合并、恢复事件和处理记录首期进入站内。站外通知、应用完全不可访问时的外部可用性探测放次期，通过独立探测端提供。没有任务或低样本失败不能自动归为网站故障。

## 7. 数据采集、历史与性能

### 7.1 数据链路

任务受理/拒绝、派发、上游结果、保存/预览、结算/退款各统一写摘要和关键事件。HTTP 层补接口 5xx、延迟和业务拒绝分类；请求日志不要把高频轮询数当生图量。

建议增加：

| 存储 | 作用与建议保留期 |
| --- | --- |
| `ops_task_facts` | 每任务一条摘要，独立保存实际线路、阶段时间、结果/保存/结算状态和错误类别；保留 30 天 |
| `ops_task_events` | 受理拒绝、关键状态变化、错误及恢复；保留 14 天，不记录每次正常轮询 |
| `ops_metric_buckets` | 分钟汇总保留 7 天，小时汇总保留 90 天；按全局、线路、模型、界面聚合 |
| `ops_incidents` | 故障聚合、影响范围、确认/恢复/关闭时间；保留 90 天 |
| `ops_admin_actions` | 持久化运维操作审计；建议保留 180 天，替代仅限 500 条且未单独挂载的文件审计 |

摘要以 taskId 幂等更新，事件用唯一事件编号/阶段版本防重。终态摘要在现有任务清理前确认已归档；归档失败延后本条元数据清理并显示采集异常。日常采样与诊断写入不阻塞上游生成，失败通过有界队列、持久恢复及周期对账补齐；不得通过采集失败改变成功/扣退款结果。

聚合使用计数、耗时分桶或可合并直方图；P95 从原样本/分布计算，不能平均每分钟 P95。迟到结果与退款可修正对应时间桶，重启、刷新和重复回执不重复计数。

按时间、状态、用户、实际线路建立必要索引，使用有时间范围的聚合与分页。用户 ID、任务 ID 不作为分钟指标的高基数维度，需要时查询摘要表。

### 7.2 刷新与资源控制

实时摘要默认前台每 20 秒刷新；历史趋势与运营数据默认每 100 秒刷新，分钟数据在后台按分钟聚合。页面隐藏暂停轮询，失败退避；始终显示采集时间、统计起点与缺失区间。

浏览器请求只读取服务端最新快照，不直接触发任务表或账本扫描。实时摘要由每个服务进程唯一的采集循环更新一次，共享给所有管理员；趋势接口读取预聚合结果，并用服务端时间戳和缓存复用结果。页面重新打开或手动刷新不启动额外扫描；多实例部署时需增加跨实例共享的采集/快照协调，当前单进程部署不引入此依赖。Node 采集内存和事件循环延迟，可用内置 `monitorEventLoopDelay`，不因查看页面才开启。[Node 官方说明](https://nodejs.org/api/perf_hooks.html#perf_hooksmonitoreventloopdelayoptions)

客户端刷新间隔加入少量随机偏移，避免多个管理员同时打开页面时请求集中。采集循环、告警评估与页面轮询分别限频；任务状态变化时写关键事件，不因每次 20 秒采样重复写数据库。

容器资源与整机资源分别展示。部署一个轻量宿主机采集脚本/服务，将主机内存、CPU、磁盘、app/MySQL 容器状态写入只读快照；app 读取快照，不挂载 Docker 管理 socket。容器指标本身可由 Docker 提供。[Docker stats 官方说明](https://docs.docker.com/reference/cli/docker/container/stats/)

首期沿用现有技术栈。以 48 个模拟任务和多后台页面测试采集开销，验收时对比业务接口 P95、CPU、内存与数据库查询数量，超出预设预算时降低采样频率、缩小查询范围或预聚合。

生产采用现有 MySQL；本地文件模式的未实现历史查询显式标为未覆盖，不能返回假零值。存储保留量上线后按实际日任务量和数据库体积调整。

### 7.3 日志与权限

事件输出使用字段白名单：时间、等级、阶段、错误类别/代码/脱敏摘要、taskId/requestId、实际线路/模型、HTTP 状态、上游 traceId、结算关联及重试次数。

API Key、会话 token、Authorization、带签名资产 URL、参考图/Base64、完整请求/响应体不进入看板。现有限流日志中的原始 key 等敏感字段同时整改；无需通过直接开放 `debug_error.log` 实现日志检索。用户信息仅管理员可见，列表默认按必要字段展示，查看详情和导出经过权限检查。

为诊断日志单独配置持久目录、大小上限和轮转，并配置 Docker 容器日志轮转。Docker 的 json-file 支持 `max-size` / `max-file`。[Docker 日志官方说明](https://docs.docker.com/engine/logging/drivers/json-file/)

## 8. 分期与验收

### 第一期：运行状态与故障定位

交付运行看板、图片队列与真实任务结果、任务详情/时间线、失败分类与受影响用户、线路健康、保存/退款/结算异常、基础资源采集、站内告警、历史摘要和脱敏事件。复用现有运营统计，但修正成功率、待处理、在线/活跃等名称及定义。现有用户/流水/线路入口从故障直接跳转。

验收场景：

- 多用户模拟达到全站 48 占用，单用户不超过 6；本站排队与上游排队分开，页面刷新不影响调度。
- 模拟上游 429、5xx、超时、空结果、原图/预览失败、结算故障，归类和受影响用户准确，后续恢复可追踪。
- 已扣点但未完结的任务不增加成功数；生成成功但保存失败不被记为生成失败/应退款。
- 任务在运行表清理后仍能查询历史摘要；上线前缺失的数据明确标识。
- 默认线路解析、批量多图、恢复重启、同编号重发不会错分线路或重复计数。
- 管理员没有任何 raw 日志/凭证暴露；普通用户访问管理接口被拒绝。
- 数据过期和采集失败显示异常，查看看板不触发上游付费请求、结果重跑或账务变更。
- 48 并发模拟负载下验证采集与多个后台窗口的增量开销；真实上游负载另做受控验证。

### 第二期：处理工具与用户经营

补齐视频/旧同步请求/前端图片加载失败及页面错误的观测；添加原任务核对、保存/结算恢复、暂停派发和并发热调整的审计工具；完善首次成功、留存、点数使用漏斗和有真实凭据的收入/成本统计；增加站外通知与外部可用性探测。
